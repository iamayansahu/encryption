04 / DOCUMENTATION

Project guide

Architecture, cryptographic flow, and safe testing notes.

System architecture

All encryption and decryption in this starter happen on the client side.

01Image inputBrowser File API
→
02Key derivationPBKDF2 · SHA-256
→
03EncryptionAES-256-GCM

04PackageJSON download
↳

The recipient selects the package, supplies the same passphrase, and the browser authenticates and decrypts the ciphertext.

⌑

Why AES-GCM?

It encrypts data and detects tampering. If the package is modified or the password is wrong, decryption fails authentication.

⌘

Why PBKDF2?

It derives an encryption key from a passphrase using a random salt and repeated SHA-256 operations, making password guessing more expensive.

▦

Why visual shares?

A thresholded image is expanded into two shares. Combining them reveals a rough visual pattern; the technique is intentionally lossy.

⚑

Threat model

Keep the passphrase private and separate from the package. A compromised website could serve altered JavaScript, so hosting alone does not guarantee end-to-end security.

Project checklist

Prototype, not audited security software.

Use non-sensitive images while testing. Do not use this student project to protect high-value or regulated information without a security review.
